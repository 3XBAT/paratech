# Промпт для трансформации PRD → tasks.json

Запуск (из корня рабочей области para-tech, один раз, до старта ralph-цикла):

```bash
claude -p "$(cat docs/process/prd-to-tasks.prompt.md)" --permission-mode acceptEdits
```

Или вставьте содержимое ниже в интерактивную сессию Claude Code.

---

Ты — инициализирующий агент для долгосрочного проекта. Твоя задача — преобразовать PRD-документ в структурированный список задач, который позволит другим агентам работать инкрементально, по одной фиче за сессию.

## Входные данные
- Прочитай `CLAUDE.md` (стек, структура рабочей области и репозитория кода, жесткие правила), `docs/architecture.md` (обязательная архитектура: слои, DDD-домен, правила ARCH-NN) и PRD: `docs/prd/learning-assistant-prd-v0.4.md`.
- Прочитай существующие черновики задач в `docs/tasks/` (T-001, T-002, S-001…S-004 и эпики в `docs/tasks/README.md`) и учти их: каждый из них должен быть отражен в `tasks.json` (можно разбить или объединить).
- Формат — как в примере `docs/process/examples/tasks.example.json` (другой проект, смотри только на структуру и уровень детализации).

## Требования к выходному файлу `tasks.json` (корень репозитория)

### 1. Формат задач — строго JSON
Используй JSON, а не Markdown. Модель реже случайно изменяет или удаляет JSON-структуры.

```
{
  "project": { "name": "...", "version": "1.0", "prd_source": "docs/prd/learning-assistant-prd-v0.4.md", "created_at": "YYYY-MM-DD" },
  "agent_instructions": { ... },
  "tasks": [
    {
      "id": "TASK-001",
      "category": "functional|ui|integration|infrastructure|security",
      "priority": "critical|high|medium|low",
      "description": "Краткое описание функциональности на русском",
      "acceptance_criteria": [
        "Конкретный критерий приёмки 1",
        "Конкретный критерий приёмки 2"
      ],
      "test_steps": [
        "Шаг 1: что сделать",
        "Шаг 2: что проверить",
        "Шаг 3: ожидаемый результат"
      ],
      "dependencies": ["TASK-000"],
      "status": "pending"
    }
  ]
}
```

### 2. Принципы декомпозиции
- **Атомарность:** каждая задача выполнима за одну сессию агента. Если требует более 30 минут работы — разбей её.
- **Независимость:** минимизируй зависимости между задачами. Агент должен уметь взять задачу и завершить её, не трогая другие.
- **Тестируемость:** у каждой задачи конкретные шаги проверки, которые агент может выполнить end-to-end (не только unit-тесты, но и реальная проверка как пользователь, например запуск бинарника или `go test` на реальном сценарии).
- **Приоритизация:** сначала инфраструктура и критический путь, потом UI-улучшения.

### 3. Обязательные категории задач
Проанализируй PRD и создай задачи для:
- `infrastructure`: настройка проекта, зависимости, конфиги, CI
- `functional`: основная бизнес-логика
- `ui`: интерфейс и взаимодействие
- `integration`: связь между компонентами, API (Hub ↔ клиент, Google Calendar, email, whisper-cli)
- `security`: аутентификация по API-ключу, хранение секретов, валидация, защита от prompt injection

### 4. Правила для coding-агентов (включи в начало файла как `agent_instructions`)

```
{
  "agent_instructions": {
    "before_start": [
      "Прочитай этот файл, progress.txt, CLAUDE.md и git log --oneline -20",
      "Выбери ОДНУ задачу со статусом pending и наивысшим приоритетом",
      "Проверь, что все dependencies этой задачи имеют статус done"
    ],
    "during_work": [
      "Работай только над выбранной задачей",
      "Делай коммиты после каждого логического изменения",
      "Не трогай код, не связанный с текущей задачей"
    ],
    "before_finish": [
      "Выполни ВСЕ test_steps из задачи",
      "Меняй status на done ТОЛЬКО после успешного прохождения всех тестов",
      "Если задачу нельзя завершить автономно (нужна проверка человеком на Windows, нужное решение пользователя, внешний доступ) — поставь status blocked и опиши причину в progress.txt",
      "Напиши summary в progress.txt",
      "ЗАПРЕЩЕНО удалять или редактировать задачи — только менять status"
    ]
  }
}
```

### 5. Особенности этого проекта
- Первой задачей (после настройки инструментов) должен идти каркас архитектуры и автоматические проверки (depguard, архитектурный тест), остальные задачи зависят от него. Пакеты в задачах указывай по `docs/architecture.md`.
- Код живет в каталоге `paratech/` (отдельный git-репозиторий), организационные файлы — в корне рабочей области; команды в `test_steps` выполняются из `paratech/`.
- Стек и жесткие правила — в `CLAUDE.md` (Go, без CGO в десктопе, без облачного STT, вывод LLM не вызывает побочных эффектов и т.д.). Задачи не должны им противоречить.
- Проверки в `test_steps` для Go: `go vet`, `go test -race ./<модуль>/...`, `GOOS=windows go vet ./desktop/...`; для фронтенда: `npm run build`.
- Агент работает в среде без Windows. Задачи, результат которых можно проверить только на реальной Windows-машине (попап без кражи фокуса, захват системного звука, реальный запуск whisper-cli), оформи так: автономная часть (код, тесты, заглушки) — отдельная задача; ручная проверка — отдельная задача с префиксом `[Windows-проверка]` в description, которую агент пометит `blocked`.
- Сначала идут спайки и контракты (границы модулей), потом реализация, потому что от них зависят остальные задачи.
- Статусы: `pending`, `done`, `blocked`. Все новые задачи — `pending`.

### 6. Количество задач
Стремись к 15–50 задачам в зависимости от размера PRD. Если получается больше 50 — группируй в эпики. Если меньше 15 — возможно, задачи слишком крупные.

## Выполни
1. Прочитай PRD, `CLAUDE.md` и `docs/tasks/`
2. Выдели все функциональные требования и критерии приёмки AC-01…AC-25
3. Декомпозируй каждое требование в атомарные задачи
4. Определи зависимости между задачами
5. Расставь приоритеты (critical path первым)
6. Сгенерируй `tasks.json` в формате JSON и проверь, что он валиден (`python3 -c "import json;json.load(open('tasks.json'))"`)
7. Создай `progress.txt`, если его нет (формат — см. шаблон в существующем файле)
8. Проверь покрытие: каждый AC из PRD §16 должен встречаться хотя бы в одной задаче (добавь в конце ответа таблицу «AC → задачи»)
